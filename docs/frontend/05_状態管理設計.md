# OfficeNavi 状態管理設計（MVP）

## 1. 目的
- 画面間で一貫したデータ更新とエラー処理を実現し、保守しやすいフロント実装方針を定義する。

## 2. 状態分類

### 2.1 サーバー状態
- users: 社員一覧
- seats: 座席一覧
- currentSeat: 社員現在位置

### 2.2 UI状態
- loading: API実行中フラグ
- submitting: フォーム送信中フラグ
- errorMessage: 表示用エラーメッセージ
- successMessage: 表示用成功メッセージ
- fieldErrors: 項目単位エラー

## 3. 画面ごとの状態
| 画面 | 主なサーバー状態 | 主なUI状態 |
|---|---|---|
| SCR-001 社員一覧 | users | loading, errorMessage |
| SCR-002 社員登録 | なし（送信のみ） | submitting, fieldErrors, errorMessage, successMessage |
| SCR-003 座席登録 | users, seats | loading, submitting, errorMessage, successMessage |
| SCR-004 現在位置照会 | currentSeat | loading, submitting, errorMessage |

## 4. データ取得/更新戦略
- users
  - 取得: SCR-001初期表示、SCR-003初期表示
  - 更新: 社員登録成功後に再取得
- seats
  - 取得: SCR-003初期表示
  - 更新: 固定マスタ想定のため操作中は再取得しない
- currentSeat
  - 取得: SCR-004照会時
  - 破棄: 画面離脱時にクリア

## 5. キャッシュ方針
- users, seatsは短時間キャッシュを許容する。
- 競合が起きやすい操作（着席登録）後は必要に応じてusers/currentSeatを再取得する。

## 6. エラー処理方針
- 400
  - バリデーションエラーを fieldErrors に格納し、各入力項目へ表示する。
- 404
  - 該当データなしとして画面上部へ表示する。
- 409
  - 業務競合としてメッセージ表示し、再選択を促す。
- 500
  - 汎用メッセージを表示し、再試行ボタンを有効化する。

## 7. 二重送信防止
- submit系操作中は submitting=true とし、送信ボタンを無効化する。
- API完了（成功/失敗）で必ず submitting=false に戻す。

## 8. 型設計方針
- APIレスポンス型はAPI単位で管理する。
- UI表示用型はAPI型を変換したViewModelを利用する。
- 日時型は表示直前に整形する。

## 9. 実装ガイド（推奨）
- APIクライアント層
  - エンドポイントごとに関数を分離し、画面から直接fetchしない。
- ストア層
  - サーバー状態とUI状態を分離して管理する。
- 画面層
  - 入力制御と表示に専念し、業務ロジックを持たせない。
